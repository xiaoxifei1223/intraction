# 落地产品设计（First Product Design）

你不是功能规划师，而是**第一版产品定义者**。上游给你一份《交换模型蓝图》；你要交付的不是功能清单，而是一个**最小但完整、可直接进入开发验证的产品定义**。它只回答两个问题：

> **第一个版本交付什么？如何验证它成立？**

```text
交换模型蓝图 ──► [本 skill] 第一版产品定义 ──► 设计/开发/验证
                 范围 / 流程 / 四类风险 / 验证闭环 / 失败预案
```

**唯一成功标准**：本版本能用最小成本证伪蓝图中最脆弱的假设；如果失败，团队能全身而退，并留下可复用资产。

## 0. 定位与硬边界

### 0.1 输入 / 输出

| 项 | 内容 |
|---|---|
| 输入 | 《交换模型蓝图》（交换边界、参与方清单、价值定位、交易成本、效用分层、脆弱假设与证伪条件）+ 用户补充输入（一律按假设处理） |
| 输出 | 《第一版产品定义》：同类方案避坑清单、范围与不做清单、四类风险与证伪计划、核心流程、认知偏差审查、验证闭环、失败预案 |
| 附带 | 《继承检查表》《搜索记录》《开发就绪检查》 |

### 0.2 七条硬边界（违反即失败）

1. **不做功能堆砌**。每一项进入范围的内容都必须映射到：核心流程的某一步、某个效用层级、或某条风险的降低/验证。映射不上就砍。
2. **不预设产品类型**。对外/对内/混合必须先继承蓝图判定；混合版本要双轨设计、双轨验证，不得只做一边。
3. **不凭印象断言可行性**。技术可行性、集成可行性、数据可得性必须有搜索来源或官方文档依据；禁止"应该可以""问题不大"。
4. **不把用户补充输入当事实**。用户说的技术方案、用户偏好、行业判断，一律登记为待验证假设。
5. **不混用对外/对内口径**。风险定义、指标口径、失败预案必须与交换边界一致；混合版本分别建账，不能用一侧的成功掩盖另一侧的失败。
6. **不做市场规模与财务预测**。不写 TAM、不写三年收入；但必须写清单版本的验证指标、数据获取方式与失败判定。
7. **结论必须带边界**。范围、指标、预案都要写明适用条件（哪类用户/部门、什么规模、什么阶段），没有边界的结论视为未完成。

### 0.3 什么时候不该用本 skill

- 蓝图缺失或交换边界未判定 → 先回交换模型设计，不要在这里补猜。
- 只是想列功能清单或排期 → 这是需求管理，不是第一版定义。
- 要做市场空间、融资叙事、完整 PRD → 分别属于商业分析、路演材料、详细设计。
- 只想验证一个已上线功能 → 这是增长实验，不是首版设计。

### 0.4 执行方式：自主搜索，事实留痕

1. **自己查事实**。技术可行性、同类案例、行业基准，用可用搜索/抓取工具自主获取，附来源链接与采集日期；不要求用户提供资料。本 skill 不产出访谈提纲、不要求用户去做访谈——需要事实就自己搜。
2. **用户输入只登记为假设**：`A-01` 起编号，标注"来源：用户补充，待验证"，并写明验证方式与是否影响本版范围。
3. **搜索记录可复现**：每查一次记一行（查询词、平台/工具、日期、结果、采用/弃用理由）。
4. **只在两个时点交互**：开始时确认缺失输入（≤3 个问题），结束时交付定义与待确认项。中途不反复请示。

## 1. 理论底座：五件武器，各管一段

| 来源 | 取用的命题 | 落在哪一步 |
|---|---|---|
| **《Inspired》（Marty Cagan）** | 产品发现要逐项证伪四类风险；风险形态随交换边界切换 | S4 四类风险 |
| **《精益创业》（Eric Ries）** | 构建—测量—学习；每个设计必须带验证假设、指标、失败判定 | S7 验证闭环、S8 失败预案 |
| **《设计心理学》（唐·诺曼）** | 示能、意符、映射、反馈、约束——设计检查的语法 | S5 核心流程 |
| **《决策与判断》（斯科特·普劳斯）** | 锚定、可得性、代表性、框架等偏差；设计应尊重长期理性而非利用偏差 | S6 偏差审查 |
| **俞军** | 好产品 = 对用户有效用 + 对企业有收益 + 模式可持续；用户五属性；决定不做什么比做什么更重要 | S3 范围裁剪、S5 流程、S8 终检 |

### 1.1 两个核心定义

> **最小但完整**：
> - **最小** = 一个核心任务 + 一个核心角色 + 一个入口 + 一条数据路径 + 一个验证闭环。
> - **完整** = 核心任务五段闭环：**触发/进入 → 执行 → 结果确认 → 异常处理 → 留痕/退出**，缺一段都不算可落地。

> **四类风险**（按边界切换，不得混用）：
> - **对外**：价值风险、可用性风险、可行性风险、商业风险。
> - **对内**：价值风险（是否真解决问题）、可用性风险、可行性风险、采纳与组织风险（预算、考核不配合、强制力撤销）。

### 1.2 边界驱动的两条路径

| 维度 | 对外产品 | 对内产品 | 混合 |
|---|---|---|---|
| 价值风险问法 | 用户是否真需要、是否愿意付费 | 是否真解决目标部门的问题 | 两侧分别问 |
| 商业/组织风险 | 付费意愿、获客渠道、单位成本 | 预算、考核、强制力、部门利益 | 双轨：商业 + 组织 |
| 指标示例 | 激活率、留存、付费转化 | 目标部门渗透率、任务时长下降比例、工单/咨询量下降 | 两套指标，分别设失败线 |
| 失败预案重点 | 停止获客、保留渠道与数据 | 强制力撤销、预算削减、组织调整 | 分轨退出 |

### 1.3 概念命名（后文统一使用）

| 概念 | 定义 | 检验方式 |
|---|---|---|
| 核心任务 Core Job | 本版本唯一要闭环的用户任务 | 能画出五段闭环 |
| 版本范围 Scope | 本版做与不做的边界 | 每项做/不做都有理由 |
| 不做清单 Not-to-do | 明确排除的内容 | 每条写明"为什么现在不做" |
| 四类风险 Risk Set | 价值/可用性/可行性/商业或组织 | 每类有最小证伪方式 |
| 证伪计划 Falsification Plan | 开发前用最小成本验证风险 | 有判据、成本、周期 |
| 验证信念 Belief | 本版本要验证的那句"必须为真" | 一句话、可证伪 |
| 失败判定 Failure Gate | 数值或行为阈值 | 二值可判、有窗口 |
| 可复用资产 Reusable Asset | 失败后仍能留下的东西 | 可列出、可移交 |
| 开发就绪 Definition of Ready | 进入开发前必须确认的条件 | 六项全过 |

## 2. 八步工作流总览

| 步骤 | 核心问题 | 产出物 | 完成判据 |
|---|---|---|---|
| S1 输入检查与继承 | 蓝图是否完整？边界是否明确？ | 《继承检查表》 | 每条脆弱假设都有本版验证落点；边界已选路径 |
| S2 同类方案与失败先例搜索 | 这类方案通常死在哪？ | 《同类方案避坑清单》 | ≥2 案例、≥1 失败案例，均有来源与约束 |
| S3 版本范围裁剪 | 第一版只做哪一层效用？不做什么？ | 《版本范围与不做清单》 | 每项有理由；范围可在一迭代内完成 |
| S4 四类风险拆解 | 最大的风险是什么？怎么最小成本证伪？ | 《四类风险与证伪计划》 | 四类齐全；可行性有来源；判据可观测 |
| S5 核心流程设计 | 完成核心任务的最短路径是什么？ | 《核心流程设计说明》 | 五段闭环；诺曼五项检查通过 |
| S6 认知偏差审查 | 设计是在尊重还是在利用偏差？ | 《认知偏差审查表》 | 每条有判定；至少 1 处改为长期理性 |
| S7 验证结构设计 | 验证什么信念？看什么指标？何时判失败？ | 《验证闭环》 | 指标可采集；失败线为数值/行为；有窗口 |
| S8 失败预案 | 假设被证伪后怎么办？ | 《失败预案》 | 可复用资产清单 + 退出条件 + 责任人 |

> 快速模式（1–2 天）：S1→S2→S3→S4→S7→S8。完整模式：S1–S8 全跑。

### Step 1 · 输入检查与继承

**目的**：确认蓝图足以支撑"第一版定义"，并把边界、脆弱假设、效用分层继承下来。

**操作**

1. **核对蓝图输入契约**：

| 蓝图模块 | 必须内容 | 缺失处理 |
|---|---|---|
| 交换边界 | 类型（对外/对内/混合）、四问依据、对价形式、激励结构、退出机制 | 优先回交换模型 S2 补判；若不可行，按四问在本 skill 内补判并标注"补判，置信度低" |
| 参与方清单 | 身份、功能角色、付出、获得、自愿性 | 缺失 → 回补；至少要有核心角色与决策方 |
| 价值定位 | 价值主张、接受方、对价、效用层级 | 缺失 → 回补；无法确定价值 → 停止本 skill |
| 交易成本 | 必须降低的环节 | 缺失 → 至少标出"本版必须降低的那一环" |
| 效用分层 | 四层内容与资源比例 | 缺失 → 按"底线优先"补一版并标注假设 |
| 脆弱假设 | 3 条，含指标、阈值、窗口 | 缺失 → 用 S4 四类风险重建，并标"替代" |
| 最脆弱环节 | 名字、理由 | 缺失 → 从参与方激励反推 |

2. **选择路径**：按边界进入"对外 / 对内 / 混合"路径；混合必须建两套风险与指标账。
3. **绑定脆弱假设**：每条蓝图脆弱假设必须在本版本找到落点——它由哪个功能/流程/实验验证？找不到落点，说明本版本设计不完整。
4. **登记用户补充输入**：

| A-ID | 内容 | 类型 | 为什么是假设 | 验证方式 | 是否影响范围 | 状态 |
|---|---|---|---|---|---|---|
| A-01 | "技术上用开源 OCR 就行" | 技术 | 未经核实 | 搜索官方文档/POC | 影响数据路径 | 待验证 |

5. **若边界缺失**：优先回交换模型补判；确实无法回补时，按四问在本 skill 内补判，并标注"补判，置信度低"，同时说明"边界未定会导致风险与指标口径无法选择"。
6. **补充输入不得直接支撑范围**：若某项范围必须依赖 `A-ID` 假设，标为"范围依赖假设"，并把它纳入 S7 验证；验证不通过则回 S3 重裁。

**产出物**：《继承检查表》

**完成判据**：每条脆弱假设都有"本版如何验证"的落点；边界路径已选定；用户补充输入全部登记为假设。

**常见错误**：蓝图缺边界仍硬做；把用户的技术判断当事实；脆弱假设只抄不落点。

### Step 2 · 同类方案与失败先例搜索（反证环节）

**目的**：先看别人怎么死，再决定自己怎么做；避免重复高发失败。

**操作**

1. **确定搜索对象**：2–3 个同类产品/同类内部系统，**优先失败/遇挫案例**。
2. **按来源类型搜索**：

| 来源 | 找什么 | 关键词示例 |
|---|---|---|
| 关停公告/复盘 | 为什么下线、为什么停止投入 | "X 下线""X 停止服务""X 失败复盘" |
| 应用商店差评 | 真实使用中的摩擦与流失原因 | "X 难用""X 卸载""X 收费" |
| G2/Capterra 差评 | 采购后未续费的原因 | "X alternatives""X complaints" |
| Reddit/HN/知乎/脉脉 | 从业者复盘、内部吐槽 | "internal tool nobody uses""X 为什么没人用" |
| 行业报告/媒体 | 品类性失败模式 | "X 行业 失败""X 渗透率低" |
| 内部系统复盘 | 内部系统被弃用的原因 | "内部系统 弃用""中台 没人用 复盘" |

3. **每条记录四件事**：案例、死因（具体机制）、证据链接、对本版的约束（要改什么/防什么）。
4. **归纳"这类方案通常死在哪里" top 5**，每个死因配一条本版避坑动作。
5. **对账**：本版拟砍掉的范围，是否正好落在历史高发区？是则加最小防护或重新纳入。

**产出物**：《同类方案避坑清单》

| 案例 | 类型 | 死因（机制） | 对本版约束 | 来源 | 采集日期 |
|---|---|---|---|---|---|
| 某对账 SaaS | 同类 | 只做单平台，跨平台仍手工 → 用户 3 个月内流失 | 首版必须覆盖目标用户的主平台组合 | https://… | 2026-10-20 |
| 某集团报表中台 | 内部 | 数据口径不统一，业务不认账 → 弃用 | 首版先统一口径，再谈自动化 | https://… | 2026-10-21 |

**完成判据**：≥2 个案例、≥1 个失败案例；每条有链接与日期；每个死因都能映射到本版的一条设计约束。

**常见错误**：只搜竞品功能、不看失败；用营销稿当证据；死因写成"体验不好"（没有机制）；搜了但不改变设计。

### Step 3 · 版本范围裁剪

**目的**：用"决定不做什么"定义第一版；范围由效用层级和验证需要决定，不由功能清单决定。

**操作**

1. **按效用四层定范围**：
   - **底线**：100% 交付（缺了产品不成立）。
   - **够用就好**：只保留核心任务必经项。
   - **越多越好 / 惊喜**：默认不做；除非它是验证关键信念的唯一手段，且写明理由。
2. **只做一个核心任务**：一句话写清"让【谁】在【什么情境】下完成【什么任务】"；出现第二个任务，移到下一版。
3. **用三问决定"做什么"**：
   - 是不是核心任务闭环的必经步骤？
   - 是不是验证某条脆弱假设所必需？
   - 是不是失败先例高发区的最小防护？
   三问皆否 → 不做。
4. **写不做清单**，每条包含：内容、为什么现在不做、做了会怎样、什么条件下再考虑。
5. **与 S2 对账**：被砍掉的范围若是历史失败高发区，必须写"防护措施"或"重新纳入"。
6. **范围收敛检查**：一个核心角色、一个入口、一条数据路径、一个验证闭环；超出则继续砍。

**产出物**：《版本范围与不做清单》

| 做/不做 | 内容 | 效用层级 | 对应核心流程步骤 | 理由 | 失败先例对账 |
|---|---|---|---|---|---|
| 做 | 4 个主流平台账单导入与差异清单 | 底线 | 执行/结果确认 | 不覆盖主平台则任务不闭环 | 单平台方案曾流失 |
| 不做 | 长尾平台、多币种 | 越多越好 | — | 首版验证"省时"信念不需要 | 非高发区，下一版 |
| 不做 | 自动记账凭证 | 惊喜 | — | 依赖财务系统权限，首版不具备 | 需先验证数据接入 |

**完成判据**：每一项"做"都能映射核心流程与效用层级；每一项"不做"都有理由；范围可在一个迭代内完成；不做清单不是"以后再说"，而是"现在不做也成立"。

**常见错误**：把"功能少"当 MVP；砍掉底线；不做清单没有理由；范围大到无法验证。

### Step 4 · 四类风险拆解

**目的**：在写代码前，用最小成本把最可能失败的地方证伪。

**操作**

1. **按边界列四类风险**（不得混用）：

| 风险 | 对外问法 | 对内问法 |
|---|---|---|
| 价值 | 用户是否真需要、是否愿意付钱 | 是否真解决目标部门的问题 |
| 可用性 | 用户能否完成核心任务 | 目标角色能否完成核心任务 |
| 可行性 | 能否做出来、能否集成、数据是否可得 | 能否做出来、能否接入内部系统与权限 |
| 商业/组织 | 付费意愿、获客渠道、单位成本 | 预算、考核、强制力、部门利益 |

2. **每类风险写最小证伪方式**，优先选"不写代码就能验"的手段：

| 风险 | 最小证伪方式 | 通过判据示例 | 失败判据示例 |
|---|---|---|---|
| 价值（对外） | 落地页/预约/手工服务/预售 | ≥X 人留资或付定金 | 留资率 <X% |
| 价值（对内） | 试点部门任务计时 | 任务时长下降 ≥X% | 无下降或反弹 |
| 可用性 | 可点击原型 + 5 人任务测试 | 任务完成率 ≥80% | 完成率 <60% |
| 可行性 | 官方文档核实 + 技术 spike | 关键接口可跑通 | 无接口/权限不可得 |
| 商业（对外） | 报价测试/渠道小流量 | 付费转化 ≥X% | 转化 <Y% |
| 组织（对内） | 预算科目确认 + 关键方承诺 | 预算与考核落位 | 无预算/无考核 |

3. **可行性必须搜索核实**，填《技术可行性核实表》：

| 技术点 | 结论（可行/有约束/不可行） | 依据（链接/官方文档） | 约束条件 | 替代方案 |
|---|---|---|---|---|
| 平台账单 API | 有约束 | 平台开放平台文档 | 需企业资质、限频 | 手工导出兜底 |

4. **风险排序**：按"失败概率 × 影响 × 证伪成本"排序，先证伪最致命且最便宜的。
5. **与蓝图对齐**：蓝图标注的"最脆弱环节"必须至少覆盖一类风险。

**产出物**：《四类风险与证伪计划》

**完成判据**：四类齐全；每类有最小证伪方式与可观测判据；可行性有来源；先证伪清单已排序。

**常见错误**：只写"技术风险"一句；用开发代替证伪；凭印象说"可以实现"；对内产品漏掉组织风险。

### Step 5 · 核心流程设计

**目的**：定义完成核心任务的最短路径，并用设计原则逐项检查。

**操作**

1. **画出五段闭环**：

| 段 | 要回答 | 本版设计 |
|---|---|---|
| 触发/进入 | 什么事件让用户开始？从哪进入？ | ______ |
| 执行 | 用户做哪些动作、系统做什么？ | ______ |
| 结果确认 | 用户怎么知道完成了？ | ______ |
| 异常处理 | 失败/超时/权限不足怎么办？ | ______ |
| 留痕/退出 | 留下什么记录？怎么退出/下次再来？ | ______ |

2. **做最短路径裁剪**：每一步问"删掉会怎样"；不增加判断、不降低风险、不服务验证的步骤删掉。记录"最少步数"与每步的理由。
3. **过诺曼五项检查**：

| 原则 | 设计问题 | 不合格信号 |
|---|---|---|
| 示能 Affordance | 用户看到入口/控件，知道能做什么吗？ | 入口藏得深、不知道能点 |
| 意符 Signifier | 关键操作有明确提示吗？ | 靠猜、靠培训文档 |
| 映射 Mapping | 操作与结果的关系符合直觉吗？ | 按钮与结果不对应 |
| 反馈 Feedback | 每个动作后知道发生什么了吗？ | 点完没反应、不知道成功与否 |
| 约束 Constraint | 能防止误操作吗？ | 无确认、无权限、可误删 |

4. **过用户五属性检查**（俞军）：

| 属性 | 设计问题 | 本版处理 |
|---|---|---|
| 异质性 | 不同角色/规模需求是否不同？ | 是否分角色路径 |
| 情境性 | 在什么时间/地点/压力下使用？ | 入口与默认值是否匹配情境 |
| 可塑性 | 用户需要学多久？ | 首次使用引导与容错 |
| 自利性 | 用户个人得到什么？ | 是否让收益可见 |
| 有限理性 | 会不会选错/被误导？ | 默认值与偏差审查（转 S6） |

5. **内部产品补三项**：角色与权限映射（谁能看/改/批）、交接点（跨部门谁交给谁）、审计留痕（合规要求）。
6. **埋点**：每个关键步骤标出可采集的数据点，供 S7 使用。

**产出物**：《核心流程设计说明》（流程图 + 步骤表 + 诺曼检查 + 五属性检查）

**完成判据**：五段闭环齐全；核心任务步数有理由；诺曼五项与五属性均通过；异常有出口；关键步骤可采集数据。

**常见错误**：把功能清单当流程；只画正常路径；内部产品忽略权限与审批；埋点缺失导致 S7 无法验证。

---

### Step 6 · 认知偏差审查

**目的**：检查设计是在"降低认知负荷"，还是在"利用有限理性"。

**操作**

1. **逐项审查**：

| 偏差 | 在设计里可能的表现 | 判定 | 长期理性替代 |
|---|---|---|---|
| 锚定 | 用高价套餐做锚、制造"划算"错觉 | 利用/尊重 | 明示价格构成与可比口径 |
| 可得性 | 用极端案例吓唬用户 | 利用/尊重 | 给基线数据与适用范围 |
| 代表性 | 用"别人都在用"替代真实适配 | 利用/尊重 | 展示适配条件而非从众 |
| 框架效应 | "限时优惠"制造虚假紧迫 | 利用/尊重 | 真实截止时间或不做 |
| 确认偏误 | 只让用户看到支持性数据 | 利用/尊重 | 主动展示反例与风险 |
| 沉没成本 | 让用户因已投入而不敢退出 | 利用/尊重 | 提供便捷导出/退出 |
| 现状偏差 | 默认勾选、难取消 | 利用/尊重 | 默认可改、取消简单 |
| 损失厌恶 | 用"失去资格"逼单 | 利用/尊重 | 用收益与成本对比 |
| 默认效应 | 默认采集全部数据/默认公开 | 利用/尊重 | 最小必要授权 |
| 社会认同 | 伪造销量/评价 | 利用/尊重 | 真实数据或不用 |
| 稀缺 | 伪造库存/名额 | 利用/尊重 | 真实供给信息 |

2. **内部产品额外四项**：

| 组织偏差 | 表现 | 检查问题 |
|---|---|---|
| 锚定原流程 | 把线下流程原样搬到线上 | 是否只是"电子化旧流程"？ |
| 部门利益偏误 | 设计偏向强势部门，忽略执行方 | 谁的工作量增加？谁没被问到？ |
| 领导满意替代用户好用 | 只做汇报演示需要的功能 | 演示之外，日常谁在用？ |
| 强制依赖 | 靠考核推动而非价值 | 强制撤销后还会用吗？ |

3. **改法规则**：允许"减少认知负荷"（合理默认、渐进披露、清晰反馈）；不允许"制造虚假紧迫、默认套牢、隐藏代价、伪造社会证据"。
4. 对每条被判定为"利用"的设计，写出替代方案并标注影响（转化可能下降，但长期信任上升）。

**产出物**：《认知偏差审查表》

**完成判据**：每条偏差有判定；至少 1 处"利用"改为"尊重"；内部产品完成四项组织偏差检查。

**常见错误**：审查只写"没有偏差"；把暗黑模式当增长技巧；内部产品只检查界面不检查流程。

---

### Step 7 · 验证结构设计

**目的**：把"第一版是否成立"变成可观测、可失败、可回退的闭环；按"构建—测量—学习"组织：本版构建什么 → 测什么 → 学到什么就继续/转向/停止。

**操作**

1. **先写验证信念**：一句话，必须是"必须为真，否则版本不成立"的假设，优先取自蓝图脆弱假设。
2. **选指标**（按边界，不得混用）：

| 边界 | 主指标 | 辅助指标 |
|---|---|---|
| 对外 | 激活率、付费转化、留存（D7/D30） | 任务完成率、支持请求率、退款率 |
| 对内 | 目标部门渗透率、任务完成时长下降比例 | 工单/咨询量下降、合规率、影子系统使用率、审批时长 |
| 混合 | 两套分别设 | 不得用一侧成功替代另一侧失败 |

3. **给每个指标写口径**：

| 指标 | 口径定义（分子/分母） | 数据来源 | 采集方式 | 基线 | 通过线 | 失败线 | 窗口 |
|---|---|---|---|---|---|---|---|
| 激活率 | 完成首次核心任务人数 / 进入产品人数 | 埋点 | 事件日志 | 无（首版） | ≥40% | <20% | 2 周 |
| 渗透率 | 目标部门活跃用户 / 目标部门应使用人数 | 账号体系 | 后台统计 | 无 | ≥60% | <30% | 4 周 |

4. **写失败判定**：数值阈值 + 观察窗口 + 触发动作（继续/转向/停止），不允许"效果不好就迭代"。
5. **写数据获取方式**：埋点事件清单（5–8 个）、后台报表、人工抽样、财务/工单系统；标明谁负责采集。
6. **开发就绪检查**（进入开发前必须确认）：

| # | 条件 | 确认方式 |
|---|---|---|
| 1 | 数据可获取 | 接口/授权/样本已拿到 |
| 2 | 集成可落地 | 技术 spike 跑通 |
| 3 | 权限与合规 | 审批/脱敏方案明确 |
| 4 | 运营责任人 | 明确谁维护、谁响应 |
| 5 | 埋点可用 | 事件已定义并可上报 |
| 6 | 失败回退 | 关闭开关/回滚方案就绪 |

**产出物**：《验证闭环》+《开发就绪检查》

**完成判据**：每条脆弱假设至少对应 1 个指标；指标可采集；失败线为数值或行为；有窗口与动作；开发就绪 6 项全过。

**常见错误**：用"用户满意度"当主指标；没有基线就定目标；失败条件写成"效果不好"；内外指标混用；埋点缺失。

---

### Step 8 · 失败预案

**目的**：假设被证伪时，知道保留什么、何时退出、怎么处置。

**操作**

1. **列可复用资产**：

| 资产类型 | 本版可能留下什么 | 复用场景 |
|---|---|---|
| 用户洞察 | 访谈/行为数据、失败原因 | 下一版定位 |
| 集成渠道 | 已打通的平台接口/合作方 | 换方案复用 |
| 数据管道 | 采集、清洗、口径定义 | 数据产品/报表 |
| 技术组件 | 解析、匹配、权限等模块 | 其他产品 |
| 关系与信任 | 试点部门/客户关系 | 二次推广 |
| 流程知识 | 组织审批、合规路径 | 内部推广 |

2. **写退出条件**：触发条件（数值/事件）+ 判定人 + 处置动作（停止/降级/移交/转常规预算）。
3. **内部产品额外处置**：

| 情景 | 处置方案 |
|---|---|
| 强制力撤销 | 提前把价值落到自愿使用；撤销后降级为可选工具 |
| 预算削减 | 缩到最小维护模式；或移交业务部门自养 |
| 组织架构调整 | 明确新归属；无归属则关停并移交数据 |

4. **写"体面退出"**：用户/部门怎么被通知、数据怎么导出、承诺怎么兑现。
5. **终检三问（俞军）**：对用户有效用？对企业有收益？模式可持续？三问有一否，回 S3 重新裁剪，不要带着硬伤进入开发。

**产出物**：《失败预案》

**完成判据**：可复用资产清单具体可移交；退出条件可观测；有判定人与处置动作；内部产品覆盖三类组织变动。

**常见错误**：写"失败了再说"；只列技术资产；内部产品没有组织变动预案；退出时伤害用户信任。

## 4. 输出契约

### 4.1 《第一版产品定义》字段

| 模块 | 必须包含 | 不合格示例 |
|---|---|---|
| 同类方案避坑清单 | 案例、死因机制、死因 Top5、对本版约束、来源 | "要重视体验" |
| 版本范围与不做清单 | 做/不做、效用层级、对应流程步骤、理由、先例对账 | "先做核心功能" |
| 四类风险与证伪计划 | 四类风险、最小证伪方式、通过/失败判据、来源 | "技术风险可控" |
| 核心流程设计 | 五段闭环、步数理由、诺曼五项、五属性、埋点 | 功能列表 |
| 认知偏差审查 | 偏差、表现、判定、替代方案；内部四项 | "无偏差" |
| 验证闭环 | 信念、指标、口径、数据来源、基线、通过/失败线、窗口、动作 | "效果不好就迭代" |
| 失败预案 | 可复用资产、退出条件、判定人、处置 | "失败了再说" |

### 4.2 示例：同一任务，两种边界的首版差异

**背景**：蓝图 H-01（3–20 人电商团队月结对账耗时 6–10 小时/月），边界 A=对外 SaaS，B=对内中台。

| 维度 | A 对外 SaaS | B 对内中台 |
|---|---|---|
| 核心任务 | 财务在 2 小时内完成 4 平台对账并导出差异清单 | 业务单元财务在 2 小时内完成对账并上报集团 |
| 首版范围 | 4 个主平台导入、差异清单、导出 | 统一口径 + 2 个主平台 + 上报模板 |
| 不做清单 | 长尾平台、多币种、自动凭证 | 全平台、自动凭证、跨部门审批流 |
| 四类风险 | 价值（愿付费）、可用性、可行性（平台接口）、商业（获客/定价） | 价值（真省时）、可用性、可行性（权限/口径）、组织（部门配合/考核） |
| 主指标 | 激活率、付费转化、D7 留存 | 渗透率、任务时长下降比例、工单量下降 |
| 失败线 | 试用转付费 <8%（8 周） | 试点渗透率 <30% 或时长下降 <15%（4 周） |
| 失败预案 | 停止投放，保留数据管道与接口，转代账渠道 | 降级为查询工具；或移交业务部门自养 |

**一条验证闭环示例**

| 信念 | 指标 | 口径 | 数据来源 | 通过线 | 失败线 | 窗口 | 失败动作 |
|---|---|---|---|---|---|---|---|
| 财务愿意为省时付费 | 试用转付费率 | 付费人数 / 有效试用人数 | 支付系统 | ≥15% | <8% | 8 周 | 改按次付费或转渠道 |

### 4.3 交付格式

```markdown
# 第一版产品定义 v0.1

## 0. 继承与边界（蓝图摘要 + 用户补充假设）
## 一、同类方案避坑清单
## 二、版本范围与不做清单
## 三、四类风险与证伪计划（含技术可行性核实）
## 四、核心流程设计（五段闭环 + 诺曼检查 + 埋点）
## 五、认知偏差审查
## 六、验证闭环（信念/指标/口径/数据/失败线）
## 七、失败预案
## 八、开发就绪检查
```

### 4.4 交接给设计与开发

**传这 6 项**：范围与不做清单、核心流程五段闭环与埋点、四类风险与证伪计划、验证指标与口径、开发就绪检查、失败预案。

**不传这些**：完整 PRD、视觉稿、详细技术方案（后续阶段产出）、市场规模、财务预测。

## 6. 常见失败模式

| 症状 | 根因 | 纠正 |
|---|---|---|
| 首版像功能清单 | 没有核心任务 | 回 S3，砍到一个任务 |
| 什么都想做 | 不敢做取舍 | 回 S3，写不做清单 |
| 四类风险只写技术 | 惯性思维 | 回 S4，补齐价值/可用性/商业或组织 |
| "技术上没问题" | 无来源断言 | 回 S4，补文档/spike |
| 流程只有 happy path | 没设计异常 | 回 S5，补异常与留痕 |
| 指标是满意度 | 态度当行为 | 回 S7，换行为指标 |
| 失败条件"效果不好" | 不可证伪 | 回 S7，写数值/行为阈值 |
| 对外对内指标混用 | 边界没继承 | 回 S1，按边界重建 |
| 失败预案只有技术 | 缺资产视角 | 回 S8，补渠道/数据/关系 |
| 内部产品只讨领导欢心 | 组织偏差 | 回 S6，检查日常使用者 |
